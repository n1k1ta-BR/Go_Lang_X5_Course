# HTTP API заказов

Решение практики из TASKS.md и домашней работы из HOMEWORK.md. Сервер проверяет своё состояние и создаёт заказы в памяти. После перезапуска заказы исчезают.

- `GET /health`: 200 и `{"status":"ok"}`.
- `POST /orders`: принимает `{"customer":"Анна"}`, возвращает 201 и заказ с полями `id`, `customer`, `status`.
- Имя очищается от пробелов по краям. Новый заказ получает статус `new` и уникальный ID.
- Пустое тело, некорректный JSON и пустое имя дают 400 с JSON-сообщением об ошибке. Хранилище при этом не меняется.
- Маршруты зарегистрированы через chi. Middleware пишет JSON-логи через slog: `method`, `path`, `status`, `duration_ms`. Имена клиентов и тела запросов не логируются.
- Дополнительно отклоняются второе JSON-значение и мусор после объекта. Пробелы после объекта разрешены.

## Запуск

Нужен Go 1.22 или новее. Откройте терминал в папке рядом с go.mod:

```bash
go mod download
go run .
```

Сервер слушает `127.0.0.1:8080`. Во втором терминале:

```bash
curl -i http://127.0.0.1:8080/health
curl -i -X POST http://127.0.0.1:8080/orders -H 'Content-Type: application/json' -d '{"customer":"Анна"}'
curl -i -X POST http://127.0.0.1:8080/orders -H 'Content-Type: application/json' -d '{"customer":" "}'
```

В терминале сервера должны появиться записи со статусами 200, 201 и 400.

## Проверка

```bash
go fmt ./...
go test ./...
go vet ./...
go build ./...
```

Тесты проверяют health, создание и сохранение заказов, очистку имени, разные ID, ошибочный ввод без изменения хранилища, JSON и Content-Type ответов, поля журнала и статусы 201/400 в нём.

## Как устроен код

- `main.go`: настройка сервера, маршруты, обработчики, JSON-ответы и журналирование.
- `memory.go`: готовое хранилище из задания.
- `main_test.go`: HTTP-тесты через httptest, без запуска отдельного сервера.
- `TASKS.md`: условие практики.
- `HOMEWORK.md`: условие домашней работы, выполнены обязательные и дополнительные пункты.
- `middleware.go`: request ID, журналирование и recovery.
- `homework_test.go`: проверки домашней работы.

`createOrder(store)` возвращает функцию-обработчик, которая сохраняет доступ к переданному хранилищу. На каждом запросе обработчик читает JSON, проверяет имя и только затем вызывает `store.Create`. После отправки ошибки `return` завершает обработку.

`accessLog` оборачивает обработчик: запоминает время начала, передаёт запрос дальше и после ответа записывает статус и длительность. Обёртка ResponseWriter из chi позволяет узнать фактический статус ответа.

## Домашняя работа

- `GET /orders/{id}`: 200 и JSON заказа; 400 для нечислового, нулевого, отрицательного ID и переполнения int; 404 для отсутствующего заказа.
- При создании возвращается `Location: /orders/<id>`.
- `id`, `status` и другие неизвестные поля запроса отклоняются с 400. Сервер сам задаёт ID и статус.
- Максимальный размер тела: 1024 байта, превышение даёт 413.
- Требуется `Content-Type: application/json` (параметр charset допустим), иначе 415.
- Каждый запрос получает номер в контексте, заголовке `X-Request-ID` и журнале. Номера уникальны в пределах запуска сервера.
- Middleware подключены в порядке requestID, accessLog, recovery. Поэтому логгер видит статус 500, записанный recovery.
- При панике до отправки ответа возвращается 500 с общим JSON-сообщением. Значение паники не выводится в ответ или журнал. Если ответ уже начат, соединение прерывается: заменить отправленный статус нельзя.
- Публичного маршрута для паники нет; recovery проверяется тестовым обработчиком.

После создания первого заказа:

```bash
curl -i http://127.0.0.1:8080/orders/1
curl -i http://127.0.0.1:8080/orders/999
curl -i http://127.0.0.1:8080/orders/abc
```

Тесты дополнительно проверяют чтение созданного заказа, Location, ошибки ID, неизвестные поля, лимит тела (включая ровно 1024 байта), Content-Type, соответствие request ID и JSON-лог 500 при панике.
